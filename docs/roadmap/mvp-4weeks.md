# MVP 4 週間ロードマップ

> このロードマップは「最小で動く `akari`」をいつ・何で確かめるかを定めるものです。
> 締切ではなく、**到達点と検証可能な事実** の宣言として扱います。

## 0. MVP のゴール（一行）

> 1 施設・50 入居者規模で、**入居者が「きもち」を残せて、介護士が moments を 30 秒で書けて、家族がフィードで読める**。

これが揃った時点で MVP 完了です。視線・音声・AI 要約・統計集計は **含めません**。

## 1. スコープ

### 含めるもの

| # | 機能 | 主要画面 | 主な利用者 |
|---|---|---|---|
| 1 | 入居者タブレット：「きもち」4 択 | `/resident/mood` | resident |
| 2 | 介護士スマホ：moments 30 秒入力 | `/caregiver/moments/new` | caregiver |
| 3 | 家族 web：moments フィード | `/family/feed` | family |
| 4 | 認証：施設ごと招待リンク制 | `/invite/[token]` | 全ロール |
| 5 | 監査ログ：重要操作の記録 | （バックエンドのみ） | facility-admin |
| 6 | ロケール：日本語 `ja-jp` のみ | — | — |

### 含めないもの（フェーズ 2 以降）

- 視線操作 / 滞留選択（`@ring-open/core/gaze` の取り込み）
- 音声会話 UI
- AI による要約・分類・物語生成
- k-anonymity 集計 / Wilson CI（PHIL 統計）
- 多言語（en, zh, ko など）
- 主治医ロール
- 面会予約・連絡帳機能
- 外部 LLM / 音声認識との接続

「含めない」は **諦め** ではなく **順序** です。フェーズ 2 以降で必ず戻ってきます。

## 2. 週ごとのマイルストーン

### Week 1：契約とスケルトン

**ゴール：型と画面の骨だけ揃う。誰も触れないが、構造が見える状態。**

- [ ] `docs/spec/akari-protocol-1.0.md` の主要セクションを埋める
- [ ] 技術スタック ADR (`docs/decisions/0001-tech-stack.md`) の決定
- [ ] リポジトリ構成（`apps/` `packages/`）の確定
- [ ] DB スキーマ草案（resident / mood / moments / invite / audit_log）
- [ ] 認証フローの仕様（招待トークン → セッション）
- [ ] ロール権限マトリクスの確定
- [ ] CI が lint + test で通る

**完了の確認方法：** `npm run lint && npm run test:run` が CI 上で緑。

### Week 2：入居者と介護士の核心 UX

**ゴール：「きもち」と「moments」が、ローカル開発環境で本当に動く。**

- [x] 入居者タブレット：mood 4 択画面（大きなタップ領域、フォーカス順序）
- [x] mood の保存 API（`@akari/core` 検証 + Server Action + デモモード）
- [x] 介護士スマホ：moments 入力フォーム（30 秒で完了する設計）
- [x] moments の保存 API（家族共有可 + 監査ログ）
- [ ] PII スクラブを通したロガー（ring-core から移植）
- [x] 監査ログの最小実装（mood 投稿・moments 投稿）
- [x] vitest による純粋関数テスト（mood / moment バリデーション）
- [x] `supabase/seed.sql` デモデータ

**完了の確認方法：** 開発機で resident → mood 送信 → caregiver でその直後の moments が一覧に出る。手動の操作時間が **30 秒以内**。

### Week 3：家族と認証

**ゴール：家族が、自分の家族の moments だけを安全に読める。**

- [ ] 家族 web：moments フィード（時系列、画像なし、テキストのみ）
- [ ] 招待トークンの発行・検証（HMAC + base64url、短時間有効）
- [ ] パスワードハッシュ：Argon2id または bcrypt(cost ≥ 12)
- [ ] ロール認可ミドルウェア（resident / caregiver / facility-admin / family）
- [ ] family ロールは自分の家族のデータのみ可視（RLS or アプリ層チェック）
- [ ] 削除権 API（resident 本人 / family の要請を facility-admin が実行）
- [ ] Playwright で 3 ロールの主要フローを E2E

**完了の確認方法：**
- 招待リンクを別ブラウザで開くと、その人のロール固有の画面に入れる
- family ロールから他家族のデータを **取得できない** ことを E2E で確認

### Week 4：仕上げと「人に見せられる」

**ゴール：1 施設の試用に出せる完成度。本番デプロイは任意。**

- [ ] アクセシビリティ：コントラスト・スクリーンリーダー・タップ領域の最終確認
- [ ] 日本語の文言レビュー（敬体・命令形を避けた書き換え）
- [ ] エラーハンドリングと再試行（オフライン耐性の最低限）
- [ ] デモシード：架空入居者 3 名、moments 30 件、家族 2 名（個人特定不能なデータ）
- [ ] `README.md` のスクリーンショット / 短い動画
- [ ] プライバシーポリシー雛形（`docs/spec/privacy-policy-1.0.md`）
- [ ] リリースノート `v0.1.0`

**完了の確認方法：** 施設関係者 1 人に 15 分触ってもらい、「**説明なしで mood を送れた**」「**moments を読めた**」と確認できる。

## 3. 各週のレビューゲート

毎週末、次の質問に **書面で** 答えてから次の週に進みます。

1. **尊厳ファースト**：今週追加した機能で、入居者が「嫌な気持ち」になりうる要素は？
2. **介護士の手数**：今週の追加で、介護士の操作時間は何秒変わった？
3. **家族の参加**：今週の追加で、家族の「参加できること」は増えた？読むだけになっていないか？
4. **データ最小**：新規保存フィールドは本当に必要だったか？
5. **削除権**：今週追加したデータは、本人 / 家族の要請でちゃんと消せるか？

書面は `docs/roadmap/reviews/week-N.md` に残します（テンプレは後日追加）。

## 4. リスクと前提

| リスク | 対応 |
|---|---|
| 技術スタック決定が遅れる | Week 1 中に ADR を必ずクローズ |
| 介護士の操作時間が 30 秒を超える | 入力項目を削る（追加ではなく削減で対処） |
| 家族 UI が「読むだけ」に閉じる | Week 3 終了時に「家族が能動的にできること」を最低 1 つ確保 |
| 施設外への意図しないデータ送出 | 全外部送信を allowlist 化、CI で検証 |
| ring-core 由来語彙の混入 | PR テンプレでチェック、レビューで指摘 |
